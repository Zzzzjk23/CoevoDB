# E1 · DuckDB 主对比 · 运行单

S19 交付（`SESSIONS.md` S19，`EXPERIMENT.md` §9 的 E1）。服务器 `ssh 3090`，命令都在服务器上执行，`PY=~/CoevoDB/.venv/bin/python`。开跑前照 `SERVER.md` §5.1 检查。

## 1. 预实验

- 配置：`framework/surprise/docs/grids/e1_pilot_c8.json`、`e1_pilot_c4.json`、`e1_pilot_c1.json`。四个臂 `full`、`nollm`、`pure-llm`、`sqlancer`，DuckDB 1.5.5，每格 2 小时，每格绑 2 个 CPU、DuckDB 2 个线程，墙钟宽限 10 分钟；三份只差并发度（8、4、1）与种子：c8、c4 用 9101、9102（各 8 格），c1 只用 9101（4 格）。
- 带 LLM 的两个臂的响应缓存放在各自的结果目录里（`results/<名字>/llm-cache/<臂>`）：三次预实验互不命中缓存，并发不同时 LLM 的真实延迟都算进去。缓存键含种子，同一臂的不同种子不会互相命中。
- 脚本 `framework/surprise/docs/runs/e1_pilot.sh` 依次跑 c8、c4、c1，每次跑完写 `status` 与报告。约 2.2 + 4.4 + 8.7 ≈ 15.3 小时。
- 启动（tmux 会话 `e1-pilot`）：

```
tmux new -s e1-pilot
cd ~/CoevoDB/framework
read -rs DEEPSEEK_API_KEY && export DEEPSEEK_API_KEY
bash surprise/docs/runs/e1_pilot.sh
```

- 结果：`~/CoevoDB/framework/results/e1-pilot-c8/`、`e1-pilot-c4/`、`e1-pilot-c1/`（每个下面 `grid.json`、`cells/<臂>/s<种子>-r0/`、`llm-cache/`、跑完后的 `report/`），日志 `results/e1-pilot-c{8,4,1}.log`。
- 看状态：`$PY -m surprise.experiments.grid status results/e1-pilot-c8`（c4、c1 同理）。
- 比什么：每个臂每格的吞吐（实验数或 SQLancer 查询数每小时）、`invalid` 里重跑不稳定与超时的比例、`nollm` 同种子在三种并发下逐条标签的一致前缀、LLM 调用量与花费。据此在 8 与 4 之间定正式并发，写进 `EXPERIMENT.md` 与正式配置。

## 1b. GLM 预实验（2026-10-21）

- 原因：LLM 角色换成了 GLM 5.3 Flash（`glm-flash` 档，推理强度 low，429 退避重试），`full` 臂在真实负载下的吞吐、限流与花费要重新量。用户的指示："现在开始跑，你只需要挂到服务器上跑，不用监控"。
- 配置 `framework/surprise/docs/grids/e1_pilot_glm.json`：只有 `full` 臂（`tier: glm-flash`），种子 9101、9102，每格 2 小时，两格同时跑（`concurrency` 2），每格 2 个 CPU、DuckDB 2 个线程，墙钟宽限 10 分钟；价格用 OpenRouter 的表。`nollm` 与 `sqlancer` 沿用上面 c8、c4 的结果，不重跑。
- 脚本 `framework/surprise/docs/runs/e1_pilot_glm.sh`：起网格，同时在后台起看守（等 `grid.json` 出现后跟着网格进程，网格结束自己停）；跑完写 `status` 与报告。约 2.2 小时。部署 tag `s19-deploy-3`。
- 启动（tmux 会话 `e1-glm`，新开的会话里已经有两把密钥）：

```
tmux new -s e1-glm
bash ~/CoevoDB/framework/surprise/docs/runs/e1_pilot_glm.sh
```

- 结果：`~/CoevoDB/framework/results/e1-pilot-glm/`，日志 `results/e1-pilot-glm.log`，看守日志 `results/e1-pilot-glm.notify.log`。看状态：`$PY -m surprise.experiments.grid status results/e1-pilot-glm`。
- 比什么：`full` 每格的吞吐（与 DeepSeek 时 c8、c4 的 `full` 比）；`cells/full/s<种子>-r0/llm/calls.jsonl` 里各角色的调用数、失败数与原因；格日志 `cells/full/s<种子>-r0.log` 里 `HTTP 429` 重试行的条数；花费。只有两格同时调 GLM，限流压力比 E1 正式（并发 8 时最多 5 个 `full` 格同时跑）小。
